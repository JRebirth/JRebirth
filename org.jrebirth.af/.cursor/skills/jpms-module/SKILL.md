# Manage JRebirth JPMS module-info

Every JRebirth client module ships `module-info.java`. Get four things right: requires exports opens ModuleStarter provider

## Decide: open module or explicit opens

JRebirth core instantiates Model, View, Controller reflection so their packages must open `org.jrebirth.af.core`.

- simplest: declare `open module name { ... }` so every package open (showcases app shell do this)
- stricter: declare plain `module` add one `opens pkg to org.jrebirth.af.core;` per package holds JRebirth components or FXML controllers

## Required reads

- `requires org.jrebirth.af.api;` `requires org.jrebirth.af.core;` minimum
- add `org.jrebirth.af.component`, `org.jrebirth.af.preloader`, `org.jrebirth.af.iconfontbridge.*` only when used
- JavaFX, JDK (`java.net.http`, `java.desktop`...), third-party modules code needs use `requires transitive` when exported type leaks them

## ModuleStarter provider (the one JRebirth provides)

```java
// XModuleStarter is generated by the JRebirth annotation processor at compile time.
provides org.jrebirth.af.api.module.ModuleStarter with your.pkg.XModuleStarter;
```

If class unresolved processor did not run: confirm JRebirth processor annotation-processor path then rebuild Do not hand-write starter

## ServiceLoader (uses / provides)

This plain JPMS service injection separate JRebirth `@Register`/`@RegistrationPoint` (which internal JRebirth needs no `provides`). Use `uses`/`provides` only real `ServiceLoader` SPIs, e.g launcher `UIProvider`. SLF4J/Logback wire themselves runtime no `requires` needed logback binding
