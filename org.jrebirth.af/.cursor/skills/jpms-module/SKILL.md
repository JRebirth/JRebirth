# Manage JRebirth JPMS module-info

Every JRebirth client module ships `module-info.java`. Four things must correct: `requires`, `exports`, `opens`, `ModuleStarter` provider

## Decide: open module or explicit opens

JRebirth core instantiates Model, View, Controller reflection so their packages must open `org.jrebirth.af.core`.

- Simplest approach: declare `open module name { ... }` so every package open runtime Showcases application shell typically use this
- Stricter approach: declare plain `module` add one `opens pkg to org.jrebirth.af.core;` per package holds JRebirth components or FXML controllers Use when want limit reflective access minimal set packages

## Required `requires` declarations

- `requires org.jrebirth.af.api;` `requires org.jrebirth.af.core;` minimum
- Add `org.jrebirth.af.component`, `org.jrebirth.af.preloader`, `org.jrebirth.af.iconfontbridge.*` only when module actually uses them
- Add JavaFX modules JDK modules (`java.net.http`, `java.desktop`, etc.), third-party modules needed code
- Use `requires transitive` only when exported type module leaks type required module (e.g., public method returning `javafx.controls` node)

## ModuleStarter provider

```java
// XModuleStarter is generated by the JRebirth annotation processor at compile time.
provides org.jrebirth.af.api.module.ModuleStarter with your.pkg.XModuleStarter;
```

If class unresolved annotation processor did not run Confirm JRebirth processor annotation-processor path rebuild Do not hand-write starter class

## ServiceLoader (`uses` / `provides`)

This standard JPMS service injection separate JRebirth's internal `@Register`/`@RegistrationPoint` mechanism (which needs no `provides`). Use `uses`/`provides` only real `ServiceLoader` SPIs, such launcher `UIProvider`. SLF4J Logback wire themselves runtime — no `requires` needed Logback binding
